================================================================================
ADDITIONAL MEMORY COST -- DUALCORE support task (-O2 only)
================================================================================

The stackmax values in the [2/2] table above measure only the MAIN task.
In the DUALCORE variants ML-KEM also spawns a SUPPORT task on the second
core, whose stack is statically pre-allocated at task creation time and
is therefore NOT included in the per-operation stackmax measurement.

Under -Os the support task stack was sized (with ~10% margin above the
observed peak) to:
  SPEED_DUALCORE  : 1,496 B
  STACK_DUALCORE  : 1,748 B

Under -O2 these sizes caused the support task to overflow. To make the
DUALCORE variants run at all under -O2, the support task stack had to
be raised manually (in components/mlkem/task_settings.h) to:
  SPEED_DUALCORE  : 2,000 B   (+504 B per operation,  +33.7%)
  STACK_DUALCORE  : 2,000 B   (+252 B per operation,  +14.4%)

This extra cost is attributable solely to -O2 and is NOT reflected in
the [2/2] table. The effective total stack of a DUALCORE operation
under -O2 is therefore (main task stackmax) + 2,000 B for the support
task, versus (main task stackmax) + 1,496 B / 1,748 B under -Os.

================================================================================
SUMMARY
================================================================================

PERFORMANCE (avg cycles)
------------------------
  -O2 is SLOWER than -Os in every single one of 45 measurements
  (5 modes x 3 security levels x 3 operations).

  Slowdown range : +25.72% .. +51.14%
  Mean slowdown  : ~36.9%

  Smallest gap   : STACK / ML-KEM-1024 / Decap            ( +25.72% )
  Largest gap    : SPEED_DUALCORE / ML-KEM-768 / Keypair  ( +51.14% )

  Per-mode mean slowdown of -O2 vs -Os:
    SPEED            : +35.6%
    SPEED_DUALCORE   : +41.2%
    STACK_XTREME     : +33.3%
    STACK            : +32.5%
    STACK_DUALCORE   : +41.9%


STACKMAX (peak stack, bytes)
----------------------------
  -O2 uses MORE stack than -Os in 44 of 45 measurements; only one
  case shows a small reduction. The magnitude of the increase varies
  strongly by mode.

  In the SPEED and SPEED_DUALCORE modes the impact is small
  (typically +1% .. +3%, with one +5.9% outlier on ML-KEM-512 Keypair).
  In the STACK and STACK_DUALCORE modes the increase sits around
  +5% .. +11%. The STACK_XTREME mode is the most sensitive, with
  stack inflation of +8% .. +19%.

  Largest single deviations:
    -0.63%   STACK         / ML-KEM-512  / Keypair   (-O2 uses less)
    +19.33%  STACK_XTREME  / ML-KEM-768  / Encap     (-O2 uses more)

  Per-mode mean stack increase of -O2 vs -Os:
    SPEED            :  +2.1%
    SPEED_DUALCORE   :  +1.6%
    STACK_XTREME     : +11.9%
    STACK            :  +5.7%
    STACK_DUALCORE   :  +7.7%

  NOTE: The DUALCORE variants incur an ADDITIONAL fixed memory cost
  under -O2 that is NOT visible in the table -- the support task
  stack had to be raised from 1,496 B (SPEED_DUALCORE) and
  1,748 B (STACK_DUALCORE) to 2,000 B to prevent overflow.
  See section "ADDITIONAL MEMORY COST" above.


CONCLUSION
----------
  -O2 is markedly worse than -Os on this ESP32 build, on BOTH axes:
  it runs ~37% slower on average across all 45 configurations and
  uses more stack in 44 of 45 cases. The penalty is most pronounced
  in the dual-core modes (>40% slower on average) and in the
  stack-conscious STACK_XTREME mode (peak stack +12% on average).
  In the DUALCORE modes -O2 also forces a larger support task
  stack (2,000 B vs 1,496 / 1,748 B under -Os) to avoid overflow,
  adding a further fixed memory cost that the per-operation
  stackmax measurement does not capture.

  The likely explanation is that -O2's more aggressive code
  generation (inlining, loop unrolling) inflates the binary and
  hurts instruction-cache behaviour on the Xtensa LX6 core, while
  also enlarging per-function stack frames. -Os, by contrast,
  produces a more compact instruction stream that fits the cache
  better on this target.

  For thesis-grade performance and memory numbers, -Os is the
  appropriate compiler flag; -O2 should not be used for this
  workload on ESP32.
